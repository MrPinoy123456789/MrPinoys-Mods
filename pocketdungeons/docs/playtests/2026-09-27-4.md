## Harness notes

- **Missed `start` (coordinator request).** I skipped starting the server at step 3 of section 4. `server status` printed `DOWN.`, and the runbook says "If the server is down, the owner is starting it; just begin the loop, which waits", so I followed that. The runbook's command table (section 3) does not list `start` at all, although `pdserver.mjs` implements it (header line 5, spawn at :211) and README lists it. Fix: add `server start` to the table and change step 3 to "if DOWN, run `server start` (unless the owner said they are starting it)".
- **`wait` swallows the player's questions (PD-79).** Exact: `server wait --player MrPinoy123456789 --timeout 240` returned `23:21:06 lemon unanswered <MrPinoy123456789> You shouldn't float ...` and `23:21:06 lemon says <MrPinoy123456789> I do not know that one yet.`; no `lemon ask` line ever came. Expected the `lemon ask` at about 23:20:21. Cause: the regex at `pdserver.mjs:333`. It should match only the agent's echo forms, which are `lemon says|asks|replies|thinks` plus `lemon mode`, and never `lemon ask`/`lemon answer`.
- **`wait` wakes on its own `say`.** The runbook (3.1) says `wait` ignores its own `lemon say` echo; in fact the echo line is `lemon says <p> ...` (third person), which the filter does not match, so the greeting woke the next `wait` at 23:19:12.
- **Workaround used:** a scratchpad loop that polls `server chat` every 3 s, drops `lemon mode|says|replies|thinks` and `lemon asks <p>`, and re-sends `lemon mode <p> llm` every 60 s. It caught both later questions within seconds.
- **Stale unanswered asks.** The `recent` list showed two `lemon_ask` events from an earlier session with `answered_by: none`, consistent with the same bug having hit a previous agent silently.
