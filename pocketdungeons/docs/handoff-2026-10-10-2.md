## PD-204: Kennels spawner wolves were passive (High)

**Claimed root cause.** `Door`/`IntervalState.dungeonId` store the namespaced
id `pocketdungeons:kennels` (set from `def.id()`), but `HostileWolves` asked
`Instances.inDungeon(pos, "kennels")`. The comparison was exact string
equality, so it never matched and every untagged Kennels wolf stayed passive.

**What changed.**

- `Instances.java` (~line 3050): `inDungeon` now calls `sameDungeonId(stored,
  asked)`, which strips the namespace (`indexOf(':')` prefix) from both sides
  before comparing, with a null guard on the stored side.
- `HostileWolves.java` (~line 91): the per-player sweep body was extracted
  unchanged to package-visible `enrageAround(level, player)` so a gametest can
  drive it (the gametest server has no dungeon dimension, so the tick's
  dimension gate cannot be exercised there).

**Tests.** `InstancesTest` (pure): bare vs namespaced both directions, plus
non-matching ids. `HostileWolvesGameTest.aKennelsWolfTargetsAPlayer`: a
registered instance carrying `pocketdungeons:kennels`, a mock player inside
its bounds, wolves beside them. Asserts an untagged wolf gets a persistent
anger target whose UUID is the player's, a CALM wolf gets none, a wolf outside
the bounds is left alone, and a HOSTILE wolf hunts outside the Kennels.

**Review points.**

- `Instances.inDungeon` has other callers besides `HostileWolves`; check none
  relied on the old exact-match behavior.
- The gametest asserts `getPersistentAngerTarget`, not `getTarget`: in this
  version `setTarget` resolves lazily and reads null until the wolf's brain
  ticks. Judge whether anger-target coverage is sufficient or whether a
  delayed `getTarget` assertion is worth adding.
- `IntervalState.dungeonId` defaults to `""` and one site null-checks it; the
  null guard in `dungeonIdPath` covers that. Confirm no other caller passes a
  null `asked`.

## PD-205: rising_lava entry landed in lava; lamp decoupled from lever (High)

**Owner's stated design** (from live conversation): a straight corridor; the
player enters one end, lever and lamp together at the other, lava floods
perpendicular to the route so the player must run the middle before it
closes. The template can only ever produce this: the `.nbt` bakes door
jigsaws on west and east only, `RoomManifest.queryAnyRotation` requires exact
mask equality, and `RisingLavaOrdeal.arm` derives the flood axis from the
lever's wall (`LayoutStamper.armExitLeverOrdeal` stamps the lever beside the
plan's exit door). So a door on a flood-adjacent wall cannot occur; the
reported "wrong axis" is best explained by the doorway apron flooding: the
door lane is the flood's centre line, covered by the last spread row, so a
player stepping in once lava had started (or lingering at the threshold)
landed in lava.

**What changed.**

- `RisingLavaOrdeal.java`: `LavaRoom` carries a `Set<BlockPos> aprons`
  computed at arm time by `doorAprons(level, origin)` (detects carved
  doorways via `hasDoorway`, 4 tiles each: columns DOOR_MIN..DOOR_MAX, depth
  2 rows). `placeLavaRow`/`placeLava` skip apron tiles; `removeLavaRow` needs
  no change (it only removes). Aprons stay dry even at `MAX_SPREAD` (7),
  which covers the whole interior otherwise.
- `Ordeals.java` (~line 289): `placeWallLever` gained an overload taking the
  lamp position; the two-arg form delegates with `lever.above()` (unchanged
  behavior for its one other caller, `TraversalSpecs`).
- `LayoutStamper.java` (`armExitLeverOrdeal`, ~line 534): now passes the lamp
  at `DOOR_MIN - 2`, same height as the lever, one column further from the
  doorway, instead of floating above it inside the doorway's window band.
  Shared by rising_lava and collapsing_bridge: the station change affects
  both.

**Test.** `HandlerGameTest.risingLavaKeepsDoorApronsDry`: stamps
`pocketdungeons:rooms/rising_lava` at all 4 rotations, carves an extra
flood-adjacent north doorway (defensive case), arms via
`LayoutStamper.armExitLeverOrdeal`, asserts at least two doorways' aprons
detected (the template's own doors count), floods to max spread, asserts
every apron tile lava-free while the interior is covered, and asserts the
lever/lamp positions and adjacency.

**Review points.**

- The dry apron is a permanent safe ledge at each doorway. The design intent
  is a safe landing and retreat; the middle lane still fully floods, so
  progress still requires running the lava. Judge whether a permanently dry
  ledge is acceptable or should flood on the final row.
- `doorAprons` detects at arm time; a doorway carved or sealed afterward is
  not re-detected. Confirm nothing in the ordeal lifecycle carves doors late.
- `armExitLeverOrdeal` went package-visible for the test and now also moves
  the collapsing_bridge lamp. Check the bridge's station still reads well.
- The old report also mentioned "lamp in a different spot than the lever".
  The lamp-inside-window-band reading explains it (it sat above the lever at
  DOOR_MIN - 1, inside the doorway's light band); the fix moves it to
  DOOR_MIN - 2 at lever height. Confirm no other lamp source exists that
  would confuse this (e.g. the doorway window band material itself).

## PD-206: shell token claim flow not intuitive (Medium, UX)

**What changed.** New `ShellTokenListener` (`UseItemCallback`, registered in
`PocketDungeonsMod`): right-clicking a held token (MAIN_HAND only, server
only) calls `claim(serverPlayer)`, which reads the shell name via
`RoomBuilder.shellUnlockOf`, refuses (token kept, message) when the shell is
already unlocked, else consumes one token, calls `DungeonLog.unlockShell`,
and messages the player. The menu path (Home > Manage Room > Change Shell >
Unlock) is untouched. Token lore in six chest loot tables (anomaly, pocket2,
tier_1 to tier_4 drowned) changed from "Unlock it from your room's menu." to
"Right-click to unlock."

**Test.** `ShellTokenGameTest.shellTokenClaimsOnUse`: plain item returns
PASS; a minted token claims (shell recorded, stack consumed); a repeat claim
refuses without eating the token. `ShellTokenListener.token(name)` mints the
same custom-data marker the loot tables apply.

**Review points.**

  `pocketdungeons:shellUnlock` custom-data structure `shellUnlockOf` reads

- Check nothing else grants or consumes shell tokens that the lore change
  missed (grep `shellUnlock` / `KEY_SHELL_UNLOCK`).
- `claim` runs for every main-hand item use: verify `shellUnlockOf` is cheap
  and the PASS path cannot interfere with other right-click behaviors.
- Decide whether a token for an already-owned shell should do something
  smarter than a refusal (e.g. scrap it); current behavior just refuses.
