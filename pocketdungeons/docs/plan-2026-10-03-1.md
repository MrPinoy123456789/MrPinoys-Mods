# Plan 2026-10-03 #1: first-session feature batch (for Devin)

Source: `docs/playtests/2026-10-03-1.md`, the first-ever session of a fresh
player (keystone 1, Sapper's Bag). Every item below is a player request, not a
bug; the bug fixes from that session (PD-121 to PD-127) are already done and
committed as `e433efb`.

## Ground rules

- Read first: `../CLAUDE.md` (house punctuation rule), `docs/playtests/2026-10-03-1.md`,
  `docs/playtests/LIVE_CHECKS.md`, `docs/playtests/AGENDA.md` rows A2 to A5 and A9.
- **Never write an em dash or a spaced double hyphen as punctuation**, in code,
  strings, comments, docs or commits. Check before every commit:
  `grep -rn -e $'—' -e ' -- ' --include='*.java' --include='*.md' --include='*.json' .`
- Server-side only mod (Fabric, MC 26.2). No client code, no resource pack.
  Every UI is text displays, dialogs, titles, sounds, SGUI or vanilla screens.
- Work in waves. Build and run tests at the end of each wave
  (`gradlew test`, then `gradlew build`). Commit per wave on the current
  branch (`wip-lemon-harness`). Do not push.
- Match the surrounding code: javadoc that names the playtest and date for a
  rule change, constants with a reason comment, a gametest or unit test for
  every change that can be tested headless.
- Where this plan says **ASK THE OWNER**, stop and ask before implementing that
  item; do the rest of the wave meanwhile.

## Wave 1: economy and title polish

### 1. Kit top-up replaces worn tools (A4, 2026-10-03)

The complaint: "I didn't get a flint and steel when I went back home, maybe
since I had one already, but a fresh one would be better." His flint and steel
was at 4 durability.

Today: `KitTopUp.plan` treats a durability line as replaced only when missing
and never repaired (`fraction()` returns 1.0 at the calm band only, and a held
item means zero deficit).

Change:

- A durability line also counts as a deficit when the held copy is worn past a
  threshold. Start with: worn means remaining durability below 25 percent of
  max. Keep the calm-band-only rule for replacements, so a worn tool in a bad
  interval is still a cost of overstay.
- The worn copy is consumed when the fresh one is granted (a swap, not a
  duplication path). Tag rules still apply: the fresh copy carries the bag tag.
- `tools_replaced` in the `kit_topup` journal event already exists; it should
  now list the worn tools swapped out.
- **ASK THE OWNER:** the threshold (25 percent? last use?) and whether a worn
  tool also gets replaced at the mid band at some deeper wear level.

Tests: extend `KitTopUpTest`: a tool at 80 percent durability grants nothing,
a tool at 10 percent grants a swap at calm band, grants nothing at mid band,
and the worn item is removed.

### 2. Wood in chest loot (A3, 2026-10-03)

His words: "a chest drop be a wood plank every once in a while", "I'm getting
all this iron but no wood". Crafting tables exist in room decoration but do not
help without planks.

Change:

- Add an oak planks entry (2 to 4) to the tier 1 chest tables with low weight,
  so wood is a possibility on the earliest floors without flooding it. Tier 1
  is where his complaint lives; higher tiers can get planks in the same
  proportion or a themed equivalent if the owner prefers (deepslate floors
  could drop spruce, for example). Keep it simple: oak planks everywhere,
  unless the owner says theme it.
- Check `tools/gen_themed_content.py`: themed chest tables are generated. Add
  the plank entry in the generator, not by hand in 60 files, then regenerate.

Tests: extend the chest-table verification test (the one that counts entries
per table) if it asserts contents, or add a small check that tier 1 tables
contain an `oak_planks` entry.

### 3. One staggered reveal for all big text (2026-10-03)

His ask: "We should generalize the Room name and affix reveal when the player
starts a floor so that anything that uses that big text on screen effects has
the same staggered reveal."

Today: `FloorStartTitle.show` is the only staggered sequence; `showBigTitle`
in `RunLifecycle` (HOME / DESCEND headline and the home-arrival title) sends a
plain title packet. Title sending may also live in `OmenBarText` or
`DungeonScreen`; find every `ClientboundSetTitleTextPacket` call site.

Change:

- Extract the beat machinery from `FloorStartTitle` into a shared helper
  (suggest `StaggeredTitle`): a title component plus a list of subtitle lines
  that accumulate one per beat, plus the thud per beat.
- Route every big-text call site through it: floor start (name then affixes),
  HOME arrival (HOME then the key line), DESCEND, and any other title user
  found. Sites that have no extra lines keep a single beat, unchanged.
- L14 ask from 2026-10-02-2: he wanted a slightly longer delay between lines.
  Raise the beat from 15 to 20 ticks while you are in there, in one constant.

Tests: this is client-visible; a gametest can only assert the packets do not
throw and the sequence drains. Keep one gametest that a floor commit starts
and finishes a sequence without a mock player online mid-way.

## Wave 2: merchant UI and reset

### 4. Merchant shop uses the villager trade UI (L18, 2026-10-03)

His ask: "Why isn't the merchant's shop using the villager trade ui?"

Today: `StoreNPC.openShop` builds a `SimpleGui` (GENERIC_9x5) where each slot
shows the item, price and stock. `DialogScreens` already notes the gamble
station uses SGUI's `MerchantGui` (the villager trading screen), so the
pattern exists in the codebase.

Change:

- Rebuild `openShop` on `MerchantGui` with one offer per stock line. The two
  input slots are a natural fit for themed merchants that price in floor
  drops (`MerchantThemes`): emerald trades use one input, drop-priced trades
  use the drop as the first input.
- Keep stock semantics: when a line is bought out it leaves the shop for the
  rest of the run. Check whether `MerchantGui` offers support max-uses; if
  not, remove the offer when stock hits zero and re-show the GUI.
- Keep the inventory-on-tags persistence so a shop survives chunk reloads.
- Watch: `MerchantGui` may need a merchant-level/XP display; set it to never
  level up or hide it if the API allows.

Tests: `ThemedMerchantGameTest` exists; extend it so a buy decrements stock
and a sold-out line disappears, same as the SimpleGui path asserted before.

### 5. Self-serve run reset (A2, 2026-10-03)

His ask: "there should also be a feature to let me reset the run myself",
after his first run failed at omen 4 on floor 1.

**ASK THE OWNER before building:** what "reset" means.

- Same plan again (floor 1 of the same offer, same rooms), or a re-rolled
  plan at the same keystone?
- Penalty: is it free, or does it cost an omen / an interval like a quit?
- Where: the staging room (a third lever or a button on the board), the HOME
  screen, or a `/dungeon reset` command?

If the owner picks the smallest version: a RESET action beside the GO HOME
confirm path that closes the current run (`RunLifecycle` already has the
close-and-teardown path a quit takes) and opens a fresh door offer at the
same keystone with the same bag. Reuse the confirm dialog pattern from the
home lever so a misclick costs nothing.

Tests: a gametest that commits a door, resets, and asserts a new offer at
the same keystone exists and the old slot is closed.

## Wave 3: onboarding

### 6. Scripted first-visit tutorial (A5, 2026-10-03)

The player's own script, his words:

1. Lemon leads him to the bag chest and tells him to look inside.
2. "Introduce the front wall with the door on it, describe everything on that
   wall starting with the door, then the board, then to right click the door,
   then describe the lever, then tell the player to open the lever."
3. On the next floor introduce the ender chest, then three floors in a set,
   then the way home.
4. "Guide the player into the loop and then progressively add to the loop as
   we unlock new features at higher keystone levels." He also expects Lemon
   to teleport or move around; she cannot today.

Today: `StationTutorial.nag` already nags one station per home arrival,
stored per player in `DungeonLog.taskProgress`. The tutorial is the same
shape: named steps, one at a time, done forever once seen.

Change:

- New `FirstVisitTutorial` (or extend `StationTutorial` with a pre-station
  track): steps `BAG_CHEST`, `DOOR_WALL`, `ENDER_CHEST`, `SET_OF_THREE`,
  `WAY_HOME`, each with a `taskProgress` key so it fires once ever.
- Triggers: `bag_chosen` (chest line + a look-at hint), first door commit
  (the wall walkthrough: door, board, right-click, lever), first floor
  cleared (ender chest + three-floors-in-a-set), first home arrival (way
  home + banked rewards). Lines through `Lemon.say`, matching her voice.
- Lemon cannot move; use pointing text ("the door ahead of you", "the board
  on the wall") rather than her walking there.
- The stations nudge at the first home visit is already what
  `StationTutorial.nag` does; wire it to fire as the tail of the tutorial's
  home step so it reads as one tour, not two systems.
- **ASK THE OWNER:** whether the tour is per-player only, or the party leader
  drives it once per party (a second member joining mid-tour should not
  restart it for the leader).

Tests: `StationTutorialTest` exists; mirror it for the new steps: `next`
returns the right step per progress flag, steps fire in order, and a done
step never comes back.

### 7. Lemon inspects the safe room on each exit (A9/A5, 2026-10-03)

His ask: "You should be checking the state of my room (which items I made
placed and stashed) each time I leave home."

Today: `context` (the MCP/Lemon context) has no room-contents field; Lemon
sees inventory and journal only.

Change:

- On the exit-from-home transition (`RunLifecycle` has the leave-home path
  where the next door offer is shown), scan the player's safe room before it
  is despawned: blocks placed (stations, crafting table, furnaces), chest
  contents, anything on the floor. `RoomStore` is where the room is saved;
  the scan can run against the live room while it is still loaded.
- Feed it two ways:
  - A journal event `room_scan` with a compact summary (station blocks by
    name, chest item counts), so the Lemon agent can read it in `context`.
  - A `context` field `room` for the remote harness, so remote Lemon sees
    the same summary.
- Tailored tips: if a `StationTutorial` step's block is already placed, mark
  the step done without the nag; if wood/stations are missing, the next
  nag can name what is missing ("no crafting table yet") instead of the
  generic line.
- Keep it bounded: one scan per exit, one journal line, no per-tick work.
- **ASK THE OWNER:** whether Lemon says anything unprompted from the scan
  (a one-line "nice grindstone" style remark), or only feeds `context` for
  the agent to use.

Tests: unit-testable if the summarizer takes a block/item map; a gametest
that stamps a small room, places a grindstone and a chest with items,
exits, and asserts the journal event and the `context` field.

## Do not regress

- The explosion rule: only `RubbleOrdeal.blast` reacts to explosions inside
  cells; nothing in this batch touches it, but do not loosen it while in the
  area.
- `StationTutorial.nag` keeps its one-step-per-visit pacing; the tutorial
  joins it, it does not replace it.
- Kit top-up must never mint above baseline, and never duplicate a worn tool:
  the swap consumes the old one.
- SGUI `MerchantGui` and vanilla trade UI must not let the player pull items
  out of the display; keep offers server-validated the way `StoreNPC` prices
  them today.
