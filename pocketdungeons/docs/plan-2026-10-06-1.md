### 1. PD-160 iron doors

**Finding (read this first).** The reported door is almost certainly not the
connector. `TraversalSpecs.floodedHall` stamps its own containment iron doors
in every open doorway via `placeContainmentDoor`, with a stone button on the
**inside only** (`insidePos(o, wall, DOOR_MIN - 1, 2)`). A player arriving from
outside has no opener. Worse, the hall is water from x 2 to 14 at every height,
so the east door's inside button is placed in a water column and is washed off
(buttons are not waterloggable). `ConnectorStamper.applyIronDoor` still
places its lever on the frame (PD-55 not done).

**Rule (approved):** every iron door opens from the side you arrive on. No
connector is locked by design; only `access: gated` rooms lock.

**1a. Containment doors become latches (code, not redstone).** Plates and
buttons in the neighbour's doorway slot are unreliable (the neighbour's
connector or template can overwrite them, and water washes them off), so:

- In `placeContainmentDoor`, stop placing the button. Record the two lower door
  positions as latches. Add `Set<BlockPos> latchDoors` to `FloorState` (next to
  `softBreakables`, line ~194) and to `InstanceLayout` the same way
  `softBreakables` is threaded (see `InstanceLayout` constructor ~line 107,
  `InstanceRecord` line ~279 copying layout sets into `floor`). The situation
  handler has no record; follow how `LayoutStamper` collects
  `softBreakables` from stamp time (grep `softBreakables` in `LayoutStamper`
  and `Situations`) and add latches the same way.
- New class `IronDoorLatch` (server side): a `UseBlockCallback` on an iron door
  in `PocketDungeonsMod.DUNGEON_LEVEL`. If the clicked door's lower half is a
  registered latch of the clicker's record (`InstanceRegistry.byMember`),
  open both leaves of the pair (`DoorBlock.setOpen` or set `OPEN` on both
  halves of both leaves) and remember `closeAt = gameTime + 60`. Close expired
  latches from the existing per-instance tick (`Instances.onTick`; find the
  watch tick). Play the iron door open and close sounds. Return `SUCCESS`.
- Register it from wherever `StoreNPC.register()` is called.

**1b. Connector doors (`ConnectorStamper.applyIronDoor`).**

- Near side lever moves off the frame: pick, seeded by the cell origin, a spot
  on one of the near cell's other three inner walls, at y 2, where the wall
  block is solid, the block in front is air (not water, not lava) and is not
  in any doorway lane (`RoomGeometry.DOOR_MIN - 1` to `DOOR_MAX + 1`). Place a
  wall lever there facing into the room. If no spot qualifies, keep today's
  frame position. Because `ConnectorStamper` runs after room stamping
  (`LayoutStamper.applyConnectors`), the room interior is already there to
  read. Check that ordering in `LayoutStamper` before relying on it.
- Far side gets a stone button on the frame: `LayoutStamper` already knows the
  far cell and wall (the PD-62 block near line 706). Place a wall button one
  block inside the far cell beside the doorway (same `leverPos` convention,
  `DOOR_MIN - 1`, y 2), facing into the far cell. Keep the PD-62
  `ironDoorFarSideSlots` exemption.

**1c. A shut iron door explains itself.** In `IronDoorLatch`'s callback, when
the door is not a latch and is shut, send an action bar line, throttled to
once per 3 s per player:

- connector door (the position is a connector door: record them in a set the
  same way, or detect a lever in the same cell): `The lever is in this room.`
- a gated room's door (`access: gated` room at that cell, via the plan):
  `Opens when the room is solved.`
- otherwise nothing.

Return `PASS` for these so vanilla behaviour is unchanged.

**Tests.** Gametests: stamp `flooded_hall` and assert every doorway's door is a
registered latch and opens on a simulated use, then closes after 60 ticks;
stamp a connector iron door in a plain hall and assert a lever exists in the
near cell not on the frame columns, and a button exists on the far side. Add
both to the gametest class that holds the PD-55/PD-62 connector tests (grep
`ironDoorFarSideSlots` in `src/gametest`).

**Docs.** BUGS.md PD-160: cause, fix, tests. PD-55: mark resolved by this.

### 3. Resource floors pay scrap (design item 6), then no identical doors (item 3)

Do item 6 first; it removes most identical doors by itself.

**3a. Resource floors pay scrap.**

- `TripDoors.dealFirst`: drop `def.kind() == DungeonDef.Kind.RESOURCE ? 0 :`.
  `TripDoors.dealNext`: drop `resource ? 0 :` and the `resource` local. Update
  both javadocs ("A resource dungeon deals every step as 0" goes).
- `TripDoorsTest` lines ~180 to 197 assert zero steps for resource dungeons:
  rewrite them to assert resource doors deal a shuffle of 1, 2, 3 like any
  other.
- Grep for other places that special-case resource step 0 or "Pays what you
  mine" (`IntervalBanking.doorLine` if still present, `DungeonScreen`,
  `RunLifecycle`) and remove them. Resource dungeons still pay no shard and
  no vault at the finish (`RunLifecycle.isRewardKind`), and still give the
  diary page.
- `DUNGEON_STRUCTURE_DESIGN.md`: amend D12 ("pays chart scrap like any floor,
  plus what you mine; no shard, no vault; diary page on first finish"), and add
  a follow-up under section 5: "Floor level is compass plus step, so a solo
  player is never above a floor and the too easy discount never bites solo.
  Authored fixed floor levels, or a per-dungeon `levelCap`, would make it
  real. Deferred 2026-10-06."

**3b. No identical doors.**

- `TripDoors.Door` gains `int variant` (0 for the first copy). Keep a
  4-argument constructor that passes 0 so other callers compile.
- After both deals fill `doors`, run `assignVariants(doors)`: for slot i,
  variant = the number of earlier slots with the same `dungeonId` and `nodeId`.
- The affix trap: four call sites union `AffixMath.effective(owner, level,
  offer.affixes(), defs)`, which re-adds the default seeded set:
  `DungeonScreen.previewContent` (~line 287), `RunLifecycle` (~line 691),
  `Instances` (~lines 1149 and 1461). Add one helper
  `Keystone.dealtAffixes(UUID owner, Offer offer)` that returns the final set,
  wrapped in `NodeStamper.dealtAffixes(..., dungeonId, nodeId)`, and make all
  four call sites use it.
- The helper: variant 0 is today's set. For variant v > 0, draw the seeded
  affixes with `AffixMath.seededFor` but a different seed: add an overload
  `seededFor(UUID owner, int level, List<AffixDefinition> defs, long salt)`
  that mixes `salt` into `seed(owner, level)`; salt =
  `TripDoors.seed(owner, dungeonId, nodeId, pathLength, 10 + attempt)`. Retry
  attempt 0, 1, 2, ... (at most 16) until the set (after the node's signature
  affix is added and Feral is stripped on a dark node) differs from every
  earlier copy's set; keep the last try if none differs. Same count as the
  level gives. `pathLength` must be on the offer or the door so preview and
  commit agree: put it on `Door` too.
- Under compass 5 the count is 0: leave it (approved Q3). Copies then differ
  by step only.
- Delete `DungeonScreen.identicalDoor` and the `Same as door n` line.
- Tests: in `TripDoorsTest`, variants are 0, 1, 2 for a one-edge node.
  In `AffixMathTest`, the salted overload is stable and differs from the
  unsalted pick for some salt. A new pure test (or in `KeystoneOfferTest` if it
  is pure) that deals every node of every shipped dungeon for 200 owners at
  levels 5, 11, 30 and asserts no two doors share floor, step, cost and
  affixes. If `Keystone` is not pure, put the reroll loop in a pure class
  (`DoorAffixes`) and test that.
- BUGS.md: PD-153 already says superseded; add a line pointing at this fix.

### 4. Door board and GO HOME board (design items 1 and 2)

**4a. Two displays.** `DungeonScreen.summonDoor` / `updateDoor` / `show`
currently put the whole board in one display at `DOOR_SCALE` 2.0. Split like
`summonHistory`: a title display (line 1, scale 2.0) and a body display (the
rest, scale 1.6), each with its own anchor, both tagged `TAG`. Title anchored
so its bottom sits at `DOOR_CENTER_Y + 0.5` (top half of the two-row backdrop
at y 4 to 6), body centred in what is left below. Keep the update-in-place
logic for both (search radius must find two displays now: match on scale or
add a second tag such as `pocketdungeons_screen_body`). `refusalContent` and
`idleContent` can render as title + body too (first line title).
`DungeonScreen.previewContent` should return a pair (title, body); simplest is
a small record `Board(Component title, Component body)`.

**4b. Door board content** (`previewContent`), exact strings:

```
INFESTATION · floor 3 of 4                      title, yellow
Hollow Walls · Overclocked                      name white, " · Overclocked" magenta
3 scrap · 2 echo shards                         cyan
loot ×3 · costs 1 echo shard                    "loot ×3" green, " · costs ..." yellow
```

- Title: `DUNGEON_NAME_UPPER + " · floor " + node.layer() + " of " + def.layers()`.
  Endless Mine: `ENDLESS MINE · floor N` (N = `record.interval.floorIndex + 1`).
- Name line: node name, then `" · " + label` per affix, in magenta. Separator
  ` · ` (U+00B7 with spaces) everywhere.
- Cyan line, parts joined by ` · `, omitted when empty:
  1. scrap: `IntervalBanking.effectiveScrap(step, offer.level(), ownerLevel)`;
     `N scrap`; when 0 and step > 0, `too easy` in **gray** (a separate
     component, the rest stays cyan).
  2. resource dungeon only: the simplified palette. Pure helper
     `DungeonScreen.paletteWords(List<String> palette)` (or in a pure class):
     drop the namespace, strip leading `deepslate_` and trailing `_ore`, `_`
     to space, dedupe, keep order. Mineshaft gives
     `coal · copper · iron · gold`. Skip structural blocks
     (`DungeonDef.isStructuralBlock`).
  3. node rewards: `reward.displayName()` each.
  4. final node of a reward kind: `N echo shard(s)` then `vault`; then
     `diary page` only if the owner has not found that dungeon's diary
     (`DungeonLog.Entry.diaryBandsSeen()` does not contain the diary's band).
- Loot line: `loot ×N`, N = `Omen.baseRewardChests() +
  ZoneRules.of(...).bonusChests(floorCount)` where floorCount is the floor
  count this door reaches (`record.interval.floorIndex + 1`). Cost, if any:
  ` · costs N echo shard(s)` in yellow. Free: nothing.
- Extra body lines: dark `dark: bring torches` gold; dim `dim` gray;
  experimental `experimental` red; first-timer and bias lines as today.
- Remove `lootWord`, `Rewards:`, `Resources:`, `Loot:`, `Cost:`,
  `floors remaining`.

**4c. GO HOME board.** `IntervalBanking` (pure):

- `carried(Settlement s)` = `s.levels() * SCRAP_PER_CHART + s.scrapLeft()`.
- `homeScreen(Settlement now, boolean finished)` returns title `GO HOME` and a
  body:

| Carried | Body |
|---|---|
| 0 | `no scrap yet` |
| 3 | `3 scrap` / `2 more for a chart` |
| 5 | `5 scrap` / `1 chart` |
| 7 | `7 scrap` / `1 chart · 2 scrap lost` |
| 10 | `10 scrap` / `2 charts` |

  Colours (applied in `DungeonScreen.homeContent`): `N scrap` cyan, charts
  green, `2 scrap lost` gray, `2 more for a chart` gold, `no scrap yet` gray.
  Title gold, or green when `finished` (the old `DUNGEON CLEARED: GO HOME`
  title goes). Return a structured value (title, scrap line, outcome parts)
  rather than a newline string, so colouring needs no string splitting.
- Render GO HOME as title (scale 1.0) and body (0.8) displays, like 4a.
- `bankedLine`: `N scrap stayed in the dungeon.` becomes `N scrap lost.`
- `IntervalBankingTest` lines ~102 to 120 assert the old strings: update them
  to the table above. Note `scrapText` returns `3 chart scrap`; the boards
  now say `3 scrap`. Change `scrapText` to `N scrap` and fix its callers and
  test.
- `OmenBarTextTest` may assert `chart scrap` wording in `outcome`; leave
  `OmenBarText.outcome` alone unless a test or the owner says otherwise.

**4d. Docs.** `DUNGEON_STRUCTURE_DESIGN.md` D11 "The door board" paragraph:
replace with the new layout. BUGS.md: PD-151 and PD-152 lines can note the
board was reworked again on 2026-10-06.

**5b. Hidden ore in walls (design item 7).**

- `DungeonDef`: optional `hiddenOre` object `{ "pocketsMin": 0, "pocketsMax":
  2, "sizeMin": 1, "sizeMax": 3, "blocks": [...] }`; `blocks` defaults to the
  non-structural `nodePalette`. Parse and validate in `DungeonDef.problems`.
  Add it to `data/pocketdungeons/dungeon/mineshaft.json` with the four

- `NodeStamper`: after a room's declared nodes, for a floor whose dungeon has
  `hiddenOre`, seeded by cell origin and floor seed: pick pocket count, then
  for each pocket a start position inside the cell interior (x and z 1 to 14,
  y 1 to `WALL_HEIGHT - 1`) whose block and all six neighbours are solid and
  are not the shell. Grow the pocket to its size through solid enclosed
  neighbours. Set the ore and register each block as a node exactly as a
  declared node is registered (find that call in `NodeStamper`). Skip, never
  move, a pocket that would touch air.
- Pure part (choosing positions from a solid/air predicate) goes in a pure
  helper with a unit test: never touches air, never in the shell, count and
  size bounds hold, seeded stable.
- Gametest: stamp `mineshaft_seam` on a Mineshaft floor and assert any hidden
  ore is enclosed and registered.

**5c. Run storage as a container (design item 5).**
