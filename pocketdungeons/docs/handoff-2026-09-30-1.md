## Bugs to fix

1. **PD-78, `blaze_cellar` blocks a run from starting.** At keystone 5 the
   selector showed only door 1, its preview rolled `blaze_cellar`, and six
   commit attempts failed with:

   `IllegalStateException: room pocketdungeons:blaze_cellar has spanY 2 but no climbable return path from its lower story to the upper floor (spec 13.4)`

   This is now a session blocker because the player cannot choose another door
   until keystone 7. Fix the room, not the validator. Preferred fix: edit
   `src/main/resources/data/pocketdungeons/structure/rooms/blaze_cellar.nbt` so
   its lower story has a real return route that `ReturnPathValidator` accepts
   (ladder column, water column, soul sand bubble column, or solid staircase).
   Preserve the room's intended fight and loot. If the structure is too broken
   to repair safely, remove `blaze_cellar` from the selectable room pool until
   it is repaired. Do not relax `ReturnPathValidator` just to pass.

2. **PD-92, max-omen ejection duplicates interval-start items.** Confirmed by
   Lost and Found records. `Instances.failRunOmen` calls
   `InventorySwap.restoreIntervalSnapshot`, which restores the live inventory
   and also writes the same snapshot to `log.setOrphan`. The later
   `leaveVoid` snapshots the restored inventory and merges it with
   `alreadyHeld`, so identical stacks are kept in place and appended again as
   loose stacks. Fix the double-store. Suggested shape: separate "restore the
   live inventory" from "store this pack for next entry", or make the leave
   merge recognize and skip an `alreadyHeld` stack that is already represented
   by the live stack in the same slot. Preserve the crash-recovery guarantees
   in `InventoryJournal` and `LostAndFound`.

   Regression test target: simulate a max-omen ejection, then leave and re
   enter; every interval-start stack appears exactly once. Include at least one
   stack that must go loose.

3. **PD-80 reopened, `wait` still reports a false server-down.** In live use,
   `wait_events` returned `server is down (timeout)` while `status` immediately
   showed the server UP with the player online. The previous two-failed-checks
   fix did not hold. Inspect `tools/server/pdserver.mjs` wait loop and the MCP
   wrapper in `tools/server/mcp.mjs`; make the final "down" report require a
   fresh status check at the reporting point and treat event output or an
   immediately successful status as proof the server is up. Add a regression
   test if the harness has one.
